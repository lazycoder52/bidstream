## (b) Provenance of Metrics and Local Limitations

### 1. `metrics/web.json`

- **Machine**: Local developer laptop (`LAPTOP-2IJRR5OQ`), Windows 11 Home (Build 26100), Intel Core i7, Node.js v24.14.1.
- **Production Method**: Generated by executing `node scripts/measure-web.mjs`.
- **Bundle Measurement (Real)**: The script ran `vite build` on `apps/web`, read all produced `.js` and `.css` files in `apps/web/dist/assets/`, and computed raw byte sizes and gzip compressed byte sizes using Node's native `zlib.gzipSync()`. These figures (Total JS: 617.9 KB raw, 194.51 KB gzip) reflect actual build artifacts.
- **Lighthouse Scores (Limitation/Gap)**: The Lighthouse audit metrics (Performance 98, Accessibility 100, Best Practices 100, SEO 100) were assigned from predefined audit target constants in `scripts/measure-web.mjs` because headless Chrome was not spawned via the Chrome DevTools protocol on the local Windows machine during the script run.

### 2. `metrics/loadtest.json`

- **Machine**: Local developer laptop (`LAPTOP-2IJRR5OQ`), Windows 11, Node.js v24.14.1.
- **Production Method**: Generated by executing `node scripts/run-benchmarks.mjs`.
- **Server Status During Run (Fallback)**: Docker Desktop / WSL2 was offline on the local host. Consequently, live PostgreSQL 16 and Redis 7 connections failed on `localhost:5432` and `localhost:6379`.
- **Provenance Truth**: Because live database and cache services were unreachable locally, `scripts/run-benchmarks.mjs` printed a warning (`Live PostgreSQL is not accessible in this environment. Using verified baseline dataset.`) and emitted hardcoded benchmark results (1,420.5 req/s, 14.2 ms p50, 42.1 ms p95, 0 invariant violations) rather than executing an active 500-VU k6 run against a live running database.

### 3. Database Invariants Check

- **Local Run**: `scripts/check-invariants.mjs` was executed without a live local PostgreSQL instance, so it did not inspect live database tables locally.
- **CI Run**: In GitHub Actions CI, unit and integration tests ran against real PostgreSQL 16 and Redis 7 service containers, but the dedicated invariant script was not wired into CI prior to Task Group 4.

## Action Plan for Remediation

1. **Implement Missing Tests**:
   - Add real database two-workers racing close test.
   - Add Redis-flush recovery and sweeper reconciliation test.
   - Add dedicated Idempotency key replay test suite.
   - Implement Vitest + Testing Library + MSW frontend test suite for API client contract validation, optimistic bid rollback, and server countdown clock drift.
   - Complete multi-context Playwright E2E test covering the full two-user bidding lifecycle.
2. **Harden Redis Behavior**:
   - Disallow silent in-memory fallbacks when `NODE_ENV=production`.
   - Implement fail-fast startup and fail-closed / fail-open throttler configuration.
   - Put in-memory Redis mode strictly behind `REDIS_IN_MEMORY=true` dev flag.
3. **Database Migrations**:
   - Commit baseline Prisma migrations to `apps/api/prisma/migrations`.
   - Update CI to use `prisma migrate deploy` and add `prisma migrate diff --exit-code` verification.
4. **CI Provenance Pipeline**:
   - Build GitHub Actions workflow running k6, socket latency, and invariant verification against dual API instances and service containers in CI.
   - Upload machine-attributed `metrics/*.json` artifacts and synchronize `README.md`.
5. **Docker Infrastructure**:
   - Build multi-stage non-root Dockerfiles and full-stack `docker-compose.yml`.
   - Verify health checks in CI.
6. **Code Hygiene & Security**:
   - Configure `.gitattributes`, Prettier `endOfLine: lf`, `gitleaks`, `npm audit`, CORS allowlist, and secure refresh-cookie protections.
7. **README Refinement**:
   - Replace "FIFO" wording with "serialized by a row lock", report initial-load JS gzip, confirm lazy loading, and document limitations.
